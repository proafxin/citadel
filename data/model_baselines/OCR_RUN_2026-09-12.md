## Throughput

Slot-seconds available = 8,858 × 4 = 35,432. Per-page slot occupancy is decode plus prefill
(~1.1s for a ~1,500-token image at the measured 1,368 tok/s prefill), so ≈ 46.5 s/pg.

**Estimated 610–760 pages, ≈ 4.2–5.2 pages/minute.** The range brackets whether `ocr_wait` is counted as
slot occupancy; it is queue **plus** prefill and the log does not separate them. Page counts are not in the
stage line, so this is inferred, not measured — `page_count` per doc would settle it.

## `dur=` is queue position, not work

Everything was submitted at 10:48:35 and `dur` is measured from that instant, so it ranks completion order
and nothing else. Two proofs from this run:

- `INVOICE 864067.pdf` — **blocks=10**, `dur=3796.1s`
- `AFFIDAVIT OF SERVICE ( personal service).pdf` — **blocks=10**, `dur=6298.6s`, and its `ocr_gpu=15,953 ms/pg`
  is the second-lowest in the corpus

Two of the smallest documents in the set report the 15th and 25th longest durations. Do not read `dur` as
per-file cost; read `ocr_gpu × page_count`.

1. **pptx OCR is unattributed.** `Management Information Systems … .pptx` reports `dur=1879.6s` with **no**

## Conclusions

1. **Rasterization is free.** `render_wait=0`, `render_cpu` 157 ms/pg, 0.35% of decode. There is nothing to
   win at 300 DPI, in pdfium, or in the render pool.
2. **Runtime is decode tokens × pages ÷ 4 slots.** Nothing else registers.
3. **22% of slot time is queueing.** `citadel/services/capacity.py` defines four independent pools
   (`vision`, `text-structure`, `text-large`, `interactive`), each `LM_PARALLEL + LM_BUFFER = 5`, so up to
   **20 permits are issued against a 4-slot server**. The surplus queues inside llama.cpp. This does not
   cost throughput — the GPU is saturated either way — but it inflates `ocr_wait` and makes `dur` unreadable.
4. **The served quant is correct, but not for the reason it was chosen.** `UD-IQ3_XXS` was selected on
   **excel table structure** (`EXCEL_STATE.md`), and this corpus contains no excel. A direct battery against
   `UD-Q4_K_XL` — below — settles it anyway: IQ3_XXS is **1.52× faster end-to-end with no quality deficit**.
   An earlier draft of this file concluded IQ3 was the wrong quant for OCR; that was inferred from the
   GSQ-RCO-IQ3_XXS row and is **wrong for UD-IQ3_XXS**.

## OCR battery — UD-IQ3_XXS vs UD-Q4_K_XL

Same harness, same 16 docs, same `--ctx-size 131072 --parallel 4`, run back to back.
Output in `baseline_qwen38_27b_ud_iq3xxs/` and `baseline_qwen38_27b_ud_q4kxl/`.

### Runtime — IQ3_XXS wins

Token counts via `citadel.llm.count_tokens` over the stored outputs.

| | UD-IQ3_XXS | UD-Q4_K_XL | ratio |
| --- | --- | --- | --- |
| wall, 16 docs | **257.9s** | 392.9s | **1.52× slower** |
| output tokens | 14,260 | 17,282 | Q4 **+21%** |
| mean tokens/doc | 891 | 1,080 | |
| **aggregate tok/s** @ parallel 4 | **55.3** | **44.0** | Q4 **1.26× slower** |
| output bytes | 49,161 | 61,245 | |
| weights on disk | 10.9 GB | 17.5 GB | 1.61× |

Two effects compound into the 1.52× wall gap: Q4 is 1.26× slower per token **and** emits 21% more tokens
for the same 16 pages.

**IQ3_XXS converts only ~43% of its size advantage into speed.** The weight ratio predicts 1.61×;
measured per-token is 1.26×. i-quant dequantisation is compute-heavy and absorbs the rest. This is a
measurement, not an explanation of the mechanism — but it means a smaller i-quant is **not** a
proportional speed lever, and K-quants trade size for speed more efficiently despite being larger.

For scale against the older baseline: `QWEN38_27B_Q4KM_EVAL.md` measured Q4_K_M at **32 tok/s
single-stream**. Q4_K_XL here reaches 44.0 tok/s *aggregate over 4 slots* — ~1.5× from concurrency,
in line with the 1.8× recorded in `EXCEL_STATE.md`.

One defect class is Q4-only: it read a minus sign that is not there and then built analysis on it
("a negative difference is being noted"). IQ3 did not.

### Verdict

**Keep UD-IQ3_XXS.** 1.52× faster end-to-end, no measurable quality deficit, 6.6 GB less VRAM. The quant
chosen on excel grounds turns out to be the right one on OCR grounds too, by a different argument.

### Caveat

`run_ocr_full.py` runs at `temperature: 1.0, top_p 0.95, top_k 64` — sampled, not greedy. Left unmodified
because all four stored 27B baselines used it. Single-token differences carry sampling noise; judge on
pattern across documents, and treat the per-token tables above as indicative rather than decisive.

## Open

1. The 27B was chosen because "table-structure faults are unacceptable while occasional OCR defects are"
   (`TABULAR_STATE.md`). That decision was made with **no runtime column**. On a PDF-only corpus the 30B is
   better at OCR *and* reads ~3B active params/token instead of 27B dense. Not yet measured end-to-end.
2. No wall-clock baseline exists for any other model. This run is the first entry in that column, and it has
   only one row.
3. A text-layer fast path for pages that are purely digital text with no code/json/table/list/bullet is
   unbuilt. `citadel/services/pdf.py` has no text extraction at all — every page is rasterized
   unconditionally.
